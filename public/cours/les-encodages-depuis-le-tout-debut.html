1Des octets, du texte, des nombres

1.1 Tout est octet

Ta page sur le binaire l'a montré : la mémoire est découpée en octets (bytes), des cases de 8 bits qui ont chacune leur adresse. Un fichier sur ton SSD, un paquet réseau, une clé AES, un message chiffré : tout cela n'est qu'une suite d'octets. Et un octet, c'est un entier entre 0 et 255, puisque 8 bits donnent 2⁸ = 256 valeurs.

Un ordinateur ne stocke donc ni lettres, ni images, ni grands nombres : seulement des octets. Pour représenter autre chose, on fixe une convention qui dit comment passer de cette chose aux octets, et retour. Une telle convention s'appelle un encodage (encoding).

1.2 Encoder n'est pas chiffrer

Encoder (to encode), c'est changer d'écriture selon une règle publique, sans clé. N'importe qui peut décoder. Le but est pratique : afficher, transporter, stocker.

Chiffrer (to encrypt), c'est transformer un message avec une clé secrète, pour que seuls ceux qui ont la clé puissent le lire. Le but est la confidentialité.

L'image du morse

Le morse est un encodage : il traduit les lettres en traits et en points pour les faire passer par un fil télégraphique. Sa table est publique, et un message en morse n'a rien de secret. Un message chiffré ressemble plutôt à une lettre enfermée dans un coffre : sans la clé, il reste fermé, même si tout le monde sait comment le coffre est fabriqué. C'est le principe de Kerckhoffs, publié en français en 1883 : la sécurité doit reposer sur le secret de la clé, jamais sur le secret de la méthode.

À retenir

L'hexadécimal et le Base64 ne cachent rien. Un texte en Base64 a l'air illisible, mais il se décode en une commande. S'en servir pour « protéger » un mot de passe est une faille répertoriée, CWE-261 (Weak Encoding for Password). On la trouve encore régulièrement dans des équipements embarqués, comme des automates industriels ou des écrans de supervision.

Le bon vocabulaire en français

  • chiffrer (encrypt) : transformer un message avec une clé. Le message de départ est le clair (plaintext), le résultat le chiffré (ciphertext).
  • déchiffrer (decrypt) : retrouver le clair avec la clé.
  • décrypter : retrouver le clair sans la clé, en attaquant le chiffrement. C'est le travail du cryptanalyste, et ce que la plupart des défis de CryptoHack te demanderont.
  • crypter : à éviter. Les cryptographes francophones disent « chiffrer » ; « crypter » laisserait entendre qu'on chiffre sans clé, ce qui n'a pas de sens.
  • encoder, décoder : changer d'écriture, sans clé.

2ASCII : un numéro pour chaque caractère

2.1 Numéroter les caractères

Pour stocker du texte, on numérote les caractères, et on stocke les numéros. La table ASCII (American Standard Code for Information Interchange), publiée en 1963 aux États-Unis, numérote 128 caractères : les 26 lettres dans les deux casses, les 10 chiffres, la ponctuation, l'espace, et 33 caractères de contrôle. Comme 128 = 2⁷, chaque numéro tient sur 7 bits, de 0 à 127. C'est la première ligne de tes notes.

Pourquoi 7 bits, et pas 8 ?

En 1963, chaque bit coûtait cher, sur les lignes de transmission comme sur les rubans perforés des téléscripteurs, et 7 bits suffisaient pour l'anglais. Quand on transmettait sur 8 bits, le huitième servait souvent de bit de parité, pour détecter une erreur : c'est exactement le montage de la section 3.2 de ta page sur les portes logiques. Sur une liaison série (UART), le réglage 7E1 (7 bits de données, parité paire, 1 bit de stop) vient de là. Aujourd'hui, on utilise surtout 8N1 (8 bits, pas de parité, 1 bit de stop) : tu le rencontreras en configurant l'UART d'une carte STM32.

2.3 Trois régularités cachées dans la table

La table n'est pas rangée au hasard. Écris les codes en binaire, et des régularités apparaissent. Vérifie chacune dans le laboratoire ci-dessus.

Les chiffres

'0' = 0x30 et '7' = 0x37 : le chiffre hexadécimal de droite est la valeur du chiffre. La valeur d'un chiffre, c'est donc son code moins 48 : ord('7') - ord('0') = 55 − 48 = 7. Ne confonds jamais le caractère '7', qui vaut 55, avec le nombre 7.

La casse tient en un bit

'A' = 0x41 = 100 0001 et 'a' = 0x61 = 110 0001. Seul le bit de poids 32 (0x20) change. Pour passer en minuscule, on allume ce bit ; en majuscule, on l'éteint ; pour changer de casse, on l'inverse. En Python, l'opérateur ^ (XOR) inverse des bits : chr(ord('a') ^ 0x20) donne 'A'. C'est la porte XOR de ta page sur les portes logiques, appliquée à chaque paire de bits. Attention, ça ne marche que pour les lettres : '1' devient '\x11', un caractère de contrôle.

La position dans l'alphabet tient dans les 5 bits de droite

'A' = 100 0001 : ses 5 bits de droite valent 1. 'Z' = 101 1010 : 11010 = 26. Et 'a' donne 1 aussi. Pour ne garder que ces 5 bits, on fait un ET avec 0x1f = 001 1111 : ord('z') & 0x1f donne 26. Garder certains bits grâce à un ET s'appelle appliquer un masque (mask) ; on y revient en section 4.6.

2.4 En Python : chr, ord, et deux types de chaînes

ord(c) donne le numéro d'un caractère, chr(n) le caractère d'un numéro. Ce sont deux fonctions réciproques : chacune défait ce que fait l'autre.

>>> ord('A')
65
>>> chr(65)
'A'
>>> chr(ord('A') + 1)
'B'
>>> ord('AB')
TypeError: ord() expected a character, but string of length 2 found

Pour passer d'une liste de codes à un texte, on applique chr à chaque code, puis on colle les morceaux :

codes = [67, 73, 69, 76]
texte = ""
for c in codes:
    texte = texte + chr(c)    # on accumule
print(texte)                  # CIEL

C'est le même schéma d'accumulation que le calcul de la parité, dans ta page sur les portes logiques.

La cryptographie travaille sur des octets

Avant chaque opération, demande-toi quel type tu tiens : str, bytes ou int. Dans toute la page, ces trois types gardent la même couleur : str bytes int.

Comment Python affiche un bytes

Python montre chaque octet imprimable (32 à 126) comme son caractère ASCII, et tous les autres sous la forme \x suivie de deux chiffres hexadécimaux. Trois octets de contrôle ont une écriture à eux, \t, \n et \r, et l'antislash lui-même s'écrit \\.

>>> bytes([72, 105, 33])
b'Hi!'
>>> bytes([0, 65, 200, 10, 255])
b'\x00A\xc8\n\xff'
>>> len(b'\x00A\xc8\n\xff')
5
>>> list(b'Hi!')
[72, 105, 33]
>>> b'\x48\x69' == b'Hi'
True
>>> bytes([256])
ValueError: bytes must be in range(0, 256)

Ne te laisse pas tromper par l'affichage

b'\x00A\xc8\n\xff' occupe 15 caractères entre ses apostrophes, mais ne contient que 5 octets. Et dans b'Hi!', les lettres sont seulement une façon commode d'afficher les octets 72, 105 et 33 : Python a choisi de montrer les octets imprimables comme des caractères ASCII. Un bytes n'est pas du texte pour autant.

2.5 Au-delà de 127 : Unicode et UTF-8

L'ASCII ne connaît ni « é », ni « 中 », ni « ب ». Aujourd'hui, la table qui numérote tous les caractères s'appelle Unicode : plus de 150 000 caractères, chacun avec son numéro, appelé point de code (code point) et noté U+ suivi de chiffres hexadécimaux.   • Un texte en ASCII est déjà de l'UTF-8 valide : les 128 premiers caractères gardent leur octet unique. C'est ce qui a fait le succès d'UTF-8.
  • Un caractère peut valoir plusieurs octets : len('é') vaut 1, mais len('é'.encode()) vaut 2.
  • Une suite d'octets n'est pas toujours de l'UTF-8 valide. L'octet 0xc8 = 110 01000 annonce un caractère sur deux octets. S'il arrive seul, le décodage échoue :

Tu verras souvent cette erreur sur CryptoHack, en voulant afficher comme du texte des octets qui n'en sont pas : une clé, un chiffré. Ce n'est pas un bug, ces octets ne sont simplement pas du texte. Affiche-les plutôt en hexadécimal (section 3).

Latin-1, le décodage qui n'échoue jamais

L'ancien encodage Latin-1 (ISO 8859-1) associe à chaque octet de 0 à 255 le point de code de même numéro. b.decode('latin-1') réussit donc toujours, mais le résultat n'a de sens que si le texte était vraiment écrit en Latin-1. Lire en Latin-1 des octets UTF-8 donne le bug « Ã© » de ta page sur le binaire : les deux octets c3 a9 de « é » deviennent deux caractères, « Ã » et « © ».

3L'hexadécimal : deux chiffres par octet

3.1 Pourquoi un chiffré est illisible

Un bon chiffrement produit des octets qui ressemblent à du hasard : chacune des 256 valeurs est aussi probable que les autres. Or seules 95 valeurs sur 256 sont des caractères imprimables, soit environ 37 %. Voici un vrai bloc chiffré, tiré de l'exemple de l'annexe B de la norme AES (FIPS 197) :

>>> chiffre = bytes.fromhex('3925841d02dc09fbdc118597196a0b32')
>>> chiffre
b'9%\x84\x1d\x02\xdc\t\xfb\xdc\x11\x85\x97\x19j\x0b2'

Sur ses 16 octets, 4 seulement sont imprimables : 9, %, j et 2. La probabilité que les 16 octets d'un bloc le soient tous vaut (95/256)¹⁶, environ une chance sur 7,7 millions. Et les autres octets posent de vrais problèmes : 0x0a coupe la ligne, 0x00 arrête la lecture d'une chaîne en C, 0x1b envoie un ordre au terminal. Impossible de copier-coller ça dans un message ou un fichier texte.

C'est le problème que résolvent l'hexadécimal et le Base64 : écrire n'importe quels octets avec des caractères imprimables, sans ambiguïté.

3.2 Deux chiffres par octet

Ta page sur le binaire (section 3.4) l'a montré : un chiffre hexadécimal vaut exactement 4 bits, donc un octet s'écrit avec exactement 2 chiffres hexadécimaux, de 00 à ff. Pour encoder des octets en hexadécimal, on écrit chaque octet sur deux chiffres, et on colle le tout :

b'Hi!' → '486921'

'H'7248 'i'10569 '!'3321

un saut de ligne puis 'A' → '0a41', jamais 'a41'

LF100a 'A'6541

La règle des deux chiffres

Chaque octet s'écrit avec exactement deux chiffres, même s'il est petit : l'octet 10 s'écrit 0a, jamais a. Une chaîne hexadécimale qui représente des octets a donc toujours une longueur paire, égale à deux fois le nombre d'octets.

Pourquoi c'est indispensable : sans le zéro, les octets 10 et 65 donneraient « a41 », qu'on pourrait aussi bien lire « a4 1 ». Avec deux chiffres fixes, on découpe sans hésiter, par paires. Et comme toutes les paires ont la même taille, peu importe qu'on coupe depuis la gauche ou depuis la droite. C'est différent d'un nombre écrit en hexadécimal, comme 0xa0a, dont le chiffre de gauche peut être seul : on y revient en section 5.7.

Le coût : chaque octet devient deux caractères, donc des données encodées en hexadécimal prennent deux fois plus de place. Le Base64 (section 4) fait mieux.

Deux remarques de notation

La norme qui définit le Base64 (RFC 4648) définit aussi cet encodage, sous le nom de Base16 : 16 symboles de 4 bits chacun. L'hexadécimal et le Base64 sont deux membres de la même famille.

En Python et en cryptographie, on écrit plutôt les chiffres hexadécimaux en minuscules : 0x4c et 0x4C désignent le même octet. Cette page fait comme Python.

3.3 En Python

>>> b'Hi!'.hex()

>>> bytes.fromhex('486921')

>>> bytes.fromhex('48692')         # longueur impaire
ValueError: non-hexadecimal number found in fromhex() arg at position 5

Le message d'erreur est trompeur : à la position 5, il n'y a pas un mauvais chiffre, il n'y a plus rien. Python cherchait le second chiffre de la dernière paire. Deux autres pièges :

  • hex() et .hex() ne font pas la même chose. hex(255) donne '0xff' : c'est l'écriture d'un nombre, avec le préfixe 0x et sans zéro de tête (hex(10) donne '0xa'). b'\xff'.hex() donne 'ff' : c'est l'encodage d'octets, toujours deux chiffres par octet.
  • bytes.fromhex refuse le préfixe 0x : bytes.fromhex('0x48') échoue à la position 1, sur le x.

Pour écrire un seul octet sur deux chiffres, format(10, '02x') donne '0a' : 02 veut dire « au moins deux chiffres, complétés par des 0 », et x « en hexadécimal ». Dans l'autre sens, int('ff', 16) donne 255.

3.4 Sur ta Debian : xxd

En ligne de commande, xxd affiche en hexadécimal le contenu d'un fichier, ou ce qu'on lui envoie. S'il te manque : sudo apt install xxd.

$ echo -n 'Hi!' | xxd
00000000: 4869 21                                  Hi!
$ echo -n 'Hi!' | xxd -p
486921
$ echo 486921 | xxd -r -p
Hi!

Chaque ligne de xxd donne la position du premier octet (en hexadécimal), les octets par groupes de deux, puis leur lecture en ASCII, avec un point pour chaque octet non imprimable. L'option -p (plain) donne l'hexadécimal seul, -r (reverse) fait le chemin inverse.

Le saut de ligne caché d'echo

Sans l'option -n, echo ajoute un saut de ligne à la fin, et tu encodes un octet de trop :

$ echo 'Hi!' | xxd
00000000: 4869 210a                                Hi!.

Ce 0a final est une source d'erreurs classique en CTF : le Base64 ou l'empreinte (hash) d'un mot change complètement à cause de lui. Les apostrophes, elles, empêchent bash d'interpréter le point d'exclamation.

3.5 Dans l'embarqué : des octets ne sont pas une chaîne C

En C, une chaîne de caractères est un tableau de char terminé par un octet nul : c'est ainsi que strlen trouve sa longueur, en avançant jusqu'au premier 0x00. Une clé ou un chiffré peut contenir 0x00 n'importe où, ou n'en contenir aucun. Les fonctions de chaînes (strlen, strcpy, printf("%s")) coupent alors les données au premier octet nul, ou lisent au-delà du tableau s'il n'y en a pas, sans le moindre message d'erreur.

#include <stdio.h>
#include <stdint.h>
#include <stddef.h>

/* La clé de l'exemple de la norme AES (FIPS 197, annexe B). */
static const uint8_t cle[16] = {
    0x2b, 0x7e, 0x15, 0x16, 0x28, 0xae, 0xd2, 0xa6,
    0xab, 0xf7, 0x15, 0x88, 0x09, 0xcf, 0x4f, 0x3c
};

/* Des octets voyagent toujours avec leur taille : (pointeur, taille). */
void afficher_hex(const uint8_t *octets, size_t taille) {
    for (size_t i = 0; i < taille; i++)
        printf("%02x", octets[i]);   /* deux chiffres, zéro de tête : comme format(n, '02x') */
    printf("\n");
}

int main(void) {
    afficher_hex(cle, sizeof(cle));  /* 2b7e151628aed2a6abf7158809cf4f3c */
    /* strlen((const char *)cle) n'aurait aucun sens : pas d'octet nul final,
       strlen lirait au-delà du tableau (lecture hors limites). */
    return 0;
}

4Base64 : six bits par caractère

4.1 Pourquoi encore un encodage

L'hexadécimal double la taille des données : une image de 300 ko incluse dans une page web en ferait 600. Le Base64 (RFC 4648) fait mieux : il n'ajoute qu'un tiers, et n'utilise que des caractères qui passent partout (lettres, chiffres, + et /), même dans les vieux systèmes de courrier électronique qui ne transportaient que du texte.

4.2 Le principe : 3 octets, 24 bits, 4 caractères

L'hexadécimal a 16 = 2⁴ symboles : chacun porte 4 bits. Le Base64 en a 64 = 2⁶ : chacun porte 6 bits. La difficulté, c'est qu'un octet fait 8 bits, et que 8 n'est pas un multiple de 6. Il faut un nombre de bits qui se découpe à la fois en octets et en paquets de 6 : le plus petit est 24, le plus petit multiple commun de 8 et de 6.

L'égalité à retenir

3 octets = 24 bits = 4 paquets de 6 bits = 4 caractères Base64

C'est la phrase de tes notes : « 4 characters of Base64 encode three 8-bit bytes ».

L'image des verres

Trois verres de 8 cl à transvaser dans des verres de 6 cl : avec 24 cl, tu remplis exactement quatre petits verres. Au passage, les contenus se mélangent : le deuxième petit verre reçoit la fin du premier grand verre et le début du deuxième. C'est pareil avec les bits : les paquets de 6 chevauchent les frontières des octets.

Pour aller plus loin : deux Base64 pour les mêmes octets

La consigne du défi Base64 insiste : « decode the hex first ». Voici pourquoi. La chaîne hexadécimale '4869' représente 2 octets, 0x48 et 0x69, c'est-à-dire b'Hi'. Mais en tant que texte, c'est 4 caractères, '4', '8', '6' et '9', dont les codes ASCII sont 0x34, 0x38, 0x36 et 0x39.

départ'4869'str 4 caractères fromhexb'Hi'bytes 2 octets : 48 69 b64encodeb'SGk='bytes

5Des octets aux grands entiers

5.1 Pourquoi RSA a besoin d'un nombre

AES travaille directement sur des octets : il chiffre des blocs de 16 octets. RSA, lui, fait des calculs : chiffrer un message m, c'est calculer me mod n, une puissance réduite modulo un très grand nombre n. Le « mod », c'est l'arithmétique modulaire de ton programme de maths ; ta page sur le binaire l'a déjà rencontrée, puisqu'une machine de n bits calcule modulo 2n (section 5). Pour chiffrer un texte avec RSA, il faut donc le transformer en nombre, puis, après le déchiffrement, retransformer le nombre en texte. C'est l'objet du dernier défi de tes notes.

5.2 Un message est un nombre écrit en base 256

La consigne dit : on écrit chaque octet en hexadécimal, on colle le tout, et on lit le résultat comme un nombre en base 16. Il y a une façon plus directe de voir la même chose. Un octet prend 256 valeurs, de 0 à 255 : c'est exactement un chiffre de la base 256. Une suite d'octets est donc un nombre écrit en base 256, et on le lit avec la formule de ta page sur le binaire (section 2.2), chiffre × baseposition :

b'Hi!' = [72, 105, 33] =72 × 256² + 105 × 256 + 33 =4 718 592 + 26 880 + 33 =4 745 505

Trois façons de voir le même nombre

  • en base 256 : les octets 72, 105, 33 sont ses chiffres ;
  • en base 16 : 0x486921, parce que 256 = 16², donc chaque chiffre de la base 256 s'écrit avec exactement deux chiffres hexadécimaux ;
  • en base 2 : 0100 1000 0110 1001 0010 0001, parce que 256 = 2⁸.

Concaténer l'hexadécimal, comme dit la consigne, c'est la méthode des paquets de ta page sur le binaire (section 3.4), avec des paquets de 8 bits.

C'est le compteur kilométrique de ta page sur le binaire, avec des roues de 256 crans au lieu de 10 : chaque roue est un octet, et quand une roue passe de 255 à 0, elle fait avancer sa voisine de gauche.

5.3 Dans un sens : la méthode de Horner

Pour calculer la valeur, la méthode du programmeur de ta page sur le binaire (section 3.1) marche telle quelle : on lit les octets de gauche à droite et, à chaque octet, valeur = valeur × 256 + octet.

def octets_vers_entier(octets):
    valeur = 0
    for o in octets:               # o est un int de 0 à 255
        valeur = valeur * 256 + o
    return valeur

print(octets_vers_entier(b'Hi!'))  # 4745505

Multiplier par 256, c'est décaler de 8 bits : valeur * 256 + o s'écrit aussi (valeur << 8) | o. C'est le collage de la section 4.6, étendu à autant d'octets qu'on veut.

5.4 Dans l'autre sens : les divisions successives

Pour retrouver les octets d'un nombre, on applique la méthode des divisions successives de ta page sur le binaire (section 3.2), avec 256 comme diviseur. Chaque reste est un octet, et on lit les restes de bas en haut, puisque le premier reste est le chiffre de droite.

Restes lus de bas en haut : 72, 105, 33, c'est-à-dire b'Hi!'.

def entier_vers_octets(n):
    octets = []
    while n > 0:
        octets.insert(0, n % 256)   # le reste est l'octet de droite : on l'ajoute à GAUCHE
        n = n // 256
    return bytes(octets)

5.5 En Python

Python fait ces deux calculs nativement, sans rien installer :

>>> int.from_bytes(b'Hi!', 'big')
4745505
>>> (4745505).to_bytes(3, 'big')
b'Hi!'
>>> (4745505).bit_length()
23

'big' fixe l'ordre des octets : le premier octet est le chiffre de poids fort, comme quand on écrit un nombre (section 5.8). Depuis Python 3.11, c'est la valeur par défaut, mais l'écrire rend ton code plus clair. to_bytes demande la longueur voulue. Le nombre d'octets nécessaires est ⌈nombre de bits / 8⌉, ce qui s'écrit (n.bit_length() + 7) // 8 : pour 4 745 505, (23 + 7) // 8 = 3 octets.

La bibliothèque PyCryptodome, citée par la consigne, fournit les mêmes conversions sous des noms plus courts, et calcule la longueur toute seule :

>>> from Crypto.Util.number import bytes_to_long, long_to_bytes
>>> bytes_to_long(b'Hi!')
4745505
>>> long_to_bytes(4745505)
b'Hi!'

La consigne écrit from Crypto.Util.number import *, qui importe d'un coup tous les noms du module. Dans du code que tu relis, préfère importer explicitement ceux dont tu as besoin : tu sais d'où vient chaque nom.

Les noms officiels

La norme de RSA, PKCS #1 (RFC 8017), définit exactement ces deux conversions, sous les noms OS2IP (Octet String to Integer Primitive) et I2OSP (Integer to Octet String Primitive), avec le premier octet en poids fort. bytes_to_long et long_to_bytes en sont les versions PyCryptodome.

5.7 Les pièges

Les octets nuls de tête disparaissent

b'\x00Hi' et b'Hi' donnent le même nombre, 18 537, pour la même raison que 007 = 7 : un zéro à gauche ne change pas un nombre. Au retour, un octet a disparu :

>>> bytes_to_long(b'\x00Hi')
18537
>>> long_to_bytes(18537)
b'Hi'
>>> (18537).to_bytes(3, 'big')     # en imposant la longueur, on le récupère
b'\x00Hi'

En cryptographie, la longueur fait partie de la donnée : une clé de 16 octets qui commence par 0x00 reste une clé de 16 octets. C'est pour cela qu'I2OSP, dans la norme de RSA, prend toujours la longueur voulue en paramètre, et que to_bytes l'exige.

hex() n'encode pas des octets

Pour passer d'un nombre à ses octets, il est tentant d'écrire bytes.fromhex(hex(n)[2:]). Ça marche… sauf quand le nombre de chiffres est impair :

>>> hex(2570)
'0xa0a'
>>> bytes.fromhex(hex(2570)[2:])
ValueError: non-hexadecimal number found in fromhex() arg at position 3

hex() n'écrit pas de zéro de tête : 2 570 = 0x0a0a s'écrit '0xa0a'. Utilise to_bytes ou long_to_bytes, qui gèrent la longueur.

Le message doit tenir

Avec RSA, le nombre m doit être plus petit que le module n. Pour une clé de 2048 bits, le message fait donc au plus 256 octets. En Python, les entiers n'ont pas de taille limite (ta page sur le binaire, section 5) : 256 octets donnent un entier de 617 chiffres décimaux, sans aucun problème. En C, il faut une bibliothèque (section 5.8).

En vrai, on ne chiffre jamais un message brut avec RSA

Les défis RSA de CryptoHack utilisent le RSA « des manuels » (textbook RSA) : on convertit le message en nombre et on calcule me mod n. C'est parfait pour apprendre, et dangereux en vrai : un même message donne toujours le même chiffré, et certains messages trop petits se retrouvent par un simple calcul. Les vrais systèmes ajoutent d'abord un remplissage aléatoire (OAEP, défini dans PKCS #1), puis convertissent avec I2OSP. Plusieurs défis de CryptoHack consistent justement à attaquer le RSA des manuels.

5.8 Aperçu embarqué : l'ordre des octets, et les grands nombres en C

Jusqu'ici, le premier octet était le chiffre de poids fort, comme quand on écrit un nombre sur papier. Cet ordre s'appelle gros-boutiste (big-endian). L'ordre inverse, le premier octet pour le chiffre de poids faible, s'appelle petit-boutiste (little-endian). Les noms viennent des Voyages de Gulliver, où deux peuples se font la guerre pour savoir s'il faut casser un œuf par le gros bout ou par le petit.

L'image des dates

2026-11-22 commence par la plus grosse unité, l'année : c'est gros-boutiste. 22/11/2026 commence par la plus petite, le jour : c'est petit-boutiste. Les mêmes informations, rangées dans deux ordres opposés.

>>> (0x12345678).to_bytes(4, 'big').hex(' ')
'12 34 56 78'
>>> (0x12345678).to_bytes(4, 'little').hex(' ')
'78 56 34 12'
>>> int.from_bytes(b'Hi!', 'little')       # = 0x216948 : les mêmes octets, lus à l'envers
2189640
  • Gros-boutiste : bytes_to_long, la norme de RSA (I2OSP), les en-têtes des protocoles réseau (on parle d'ordre réseau, network byte order).
  • Petit-boutiste : la mémoire de ton i5 (x86-64) et celle des Cortex-M des cartes STM32. Un uint32_t qui vaut 0x12345678, rangé à l'adresse A, occupe les octets 78, 56, 34, 12 aux adresses A, A+1, A+2, A+3. Certains algorithmes ont fait le même choix : X25519 (RFC 7748) code ses clés en petit-boutiste.

À retenir

Un mauvais ordre des octets ne produit aucun message d'erreur, seulement un résultat faux qui a l'air aléatoire. Quand tu lis une norme, cherche toujours la phrase qui fixe l'ordre des octets.

Les grands nombres en C

En C, le plus grand entier standard fait 64 bits (uint64_t). Un nombre RSA de 2048 bits se range dans un tableau, par exemple 64 mots de 32 bits : c'est un nombre écrit en base 2³², dont chaque mot est un chiffre. Encore la numération positionnelle. Les bibliothèques de cryptographie embarquée, comme Mbed TLS sur STM32, additionnent et multiplient ces nombres mot par mot, avec des retenues, exactement comme les additions posées de ta page sur le binaire.

7Relecture de tes notes

Tes notes reprennent les consignes de CryptoHack. Elles sont justes, mais elles passent sous silence des détails qui comptent dès qu'on sort des exemples.

Ce qui est juste

  • L'ASCII sur 7 bits, de 0 à 127, et chr et ord, réciproques l'une de l'autre.
  • Les chiffrés contiennent des octets non imprimables, d'où le besoin d'encodages.
  • L'hexadécimal : chaque caractère devient un nombre, écrit en base 16, et on met tout bout à bout ; bytes.fromhex() et .hex().
  • Le Base64 : 6 bits par caractère, 4 caractères pour 3 octets.
  • Pour RSA, les octets mis bout à bout en hexadécimal se lisent comme un nombre ; bytes_to_long() et long_to_bytes().

Ce qu'il faut préciser

  1. chr et ord ne s'arrêtent pas à l'ASCII. Ils travaillent sur les points de code Unicode : chr(233) donne 'é', ord('中') donne 20 013. Pour l'ASCII, point de code et octet coïncident ; au-delà, un caractère occupe plusieurs octets en UTF-8 (section 2.5).
  2. « The numbers can be combined together » : seulement si chaque octet s'écrit avec exactement deux chiffres. Sans le zéro de tête, la chaîne ne se découpe plus (section 3.2).
  3. Le Base64 utilise un 65e caractère, =, pour le remplissage, et le résultat a toujours une longueur multiple de 4 (section 4.5).
  4. « Encoding » n'est pas « encryption ». Ni l'hexadécimal ni le Base64 ne protègent quoi que ce soit (section 1.2).
  5. Concaténer l'hexadécimal, c'est lire les octets en base 256, avec le premier octet en poids fort. Les octets nuls de tête se perdent au retour (section 5.7), et l'ordre inverse existe aussi (section 5.8).
  6. « Cryptosystems like RSA work on numbers » : c'est le RSA des manuels. En pratique, on ajoute un remplissage aléatoire, OAEP, avant la conversion (section 5.7).
  7. « You will first have to install PyCryptodome » : sur Debian 13, passe par un environnement virtuel ou par apt (section 5.6). Et Python sait faire la même chose sans rien installer, avec int.from_bytes et int.to_bytes.
  8. Le vocabulaire de Python. Tes notes parlent des « methods » bytes_to_long() et long_to_bytes() : ce sont des fonctions du module Crypto.Util.number. En revanche, .hex() est une méthode d'instance (on l'appelle sur un objet bytes : b.hex()), bytes.fromhex() une méthode de classe (on l'appelle sur le type lui-même), et base64.b64encode() une fonction du module base64. Cette distinction te servira dans ton cours de méthodologie de la programmation.

  3. Que valent ord('5') - ord('0'), chr(ord('q') ^ 0x20) et ord('k') & 0x1f ?
    Réponse
    5 (53 − 48) ; 'Q', car on inverse le bit de poids 32 ; 11, car k est la 11e lettre de l'alphabet (107 = 110 1011, dont les 5 bits de droite valent 01011 = 11).
  4. Encode « Key » en Base64, à la main.
    Réponse
    K = 0x4b = 0100 1011, e = 0x65 = 0110 0101, y = 0x79 = 0111 1001. Par 6 : 010010 110110 010101 111001, soit 18, 54, 21, 57, donc S, 2, V, 5. Résultat : S2V5.
  5. Décode « Q0lFTA== » à la main. Combien d'octets obtiens-tu ?
    Réponse

    Q = 16, 0 = 52, l = 37, F = 5, T = 19, A = 0. En bits : 010000 110100 100101 000101 | 010011 000000.

    Premier groupe : 01000011 01001001 01000101 = 43 49 45. Second groupe : avec ==, on ne garde qu'un octet, 01001100 = 4c ; les 4 bits restants sont du remplissage. Résultat : 43 49 45 4c, « CIEL », 4 octets.

  6. Combien de caractères Base64 pour 100 octets ? Comment se termine le résultat ?
    Réponse
    ⌈100/3⌉ = 34 groupes, donc 136 caractères. Comme 100 = 3 × 33 + 1, le dernier groupe ne contient qu'un octet : le résultat se termine par ==.
  7. Calcule à la main l'entier qui correspond à b'Ok', puis refais le chemin inverse par divisions.
    Réponse

  8. Que valent bytes_to_long(b'\x01\x00'), bytes_to_long(b'\x00\x01') et bytes_to_long(b'\x01') ? Qu'en conclus-tu ?
    Réponse
    256, 1 et 1. b'\x00\x01' et b'\x01' donnent le même nombre : à partir du nombre seul, on ne peut pas savoir s'il y avait des octets nuls au début. Il faut connaître la longueur.
  9. Pour un nombre de 2048 bits (une clé RSA), combien faut-il d'octets ? De caractères hexadécimaux ? De caractères Base64 ? Combien de chiffres décimaux au plus ?
    Réponse
    2048 / 8 = 256 octets ; 512 caractères hexadécimaux ; 4 × ⌈256/3⌉ = 4 × 86 = 344 caractères Base64 ; 2²⁰⁴⁸ − 1 a 617 chiffres décimaux, car 2048 × log₁₀ 2 ≈ 616,5.
  10. Reconnais l'écriture de ces trois chaînes, puis décode-les : 68656c6c6f, aGVsbG8=, 448378203247.
    Réponse
    De l'hexadécimal (longueur paire, chiffres 0 à 9 et a à f) : b'hello'. Du Base64 (longueur 8, un = final) : b'hello'. Un nombre décimal : long_to_bytes(448378203247) donne b'hello'. Les trois écrivent le même message.
  11. Sur ton processeur, comment l'entier 32 bits 0x0a0b0c0d est-il rangé en mémoire, de la plus petite adresse à la plus grande ?
    Réponse

  12. Programmation : complète la fonction de la section 4.6 pour encoder en Base64 une suite d'octets de longueur quelconque, remplissage compris, sans utiliser le module base64. Teste-la contre base64.b64encode sur des suites de 0 à 6 octets.
    Une solution
    import base64

ALPHABET = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/"

def b64(octets):
    sortie = ""
    for i in range(0, len(octets), 3):
        groupe = octets[i:i + 3]
        n = len(groupe)                        # 1, 2 ou 3 octets
        groupe = groupe + bytes(3 - n)         # complète avec des octets nuls
        x = (groupe[0] << 16) | (groupe[1] << 8) | groupe[2]
        quatre = "".join(ALPHABET[(x >> d) & 0x3F] for d in (18, 12, 6, 0))
        sortie += quatre[:n + 1] + "=" * (3 - n)
    return sortie

for k in range(7):
    donnees = bytes(range(250, 250 + k))
    assert b64(donnees) == base64.b64encode(donnees).decode()
print("tout est juste")

    Pourquoi n + 1 caractères utiles : n octets font 8n bits, et il faut ⌈8n/6⌉ caractères pour les porter, soit 2 pour 1 octet, 3 pour 2 octets, 4 pour 3 octets. C'est toujours n + 1. Pour aller plus loin, écris la fonction inverse, qui décode.
